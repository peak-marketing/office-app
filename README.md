# 오피스매칭 (가칭) — 공간 탐색·3D·시공 경쟁입찰·입점 쇼핑

**개발 인수인계:** 새 개발자는 [DEVELOPER_HANDOFF.md](DEVELOPER_HANDOFF.md)부터 읽으세요. 현재 기능·실제 연동 상태·실행·검사·후속 작업과 초기 도면 생성 자료 위치를 정리했습니다.

공간 게시물에서 구상하고, 내 공간의 평면·3D를 만들고, 같은 요청 기준으로 시공 제안을 비교하거나 가구·소품을 구매하는 플랫폼입니다. 사무실과 주거를 지원합니다. 업체 제안은 서로 비공개이며 고객이 선택합니다. 쇼핑·교환·환불·정산 기록은 구현됐고 실제 결제·메일·자동 지급은 운영 연동 전입니다.

**현재 구현 범위**는 [docs/v2-plan.md](docs/v2-plan.md), AI 도면 인식과 주소별 등록 도면은 [docs/ai-floorplans.md](docs/ai-floorplans.md)를 기준으로 봅니다. 아래 회차별 설명은 개발 이력이며 현재 기능 목록과 다를 수 있습니다.

2026-10-08 기준으로 집·사무실 신청 첫 단계의 주소·동·층·호 조회와 건축물대장 전용면적 불러오기를 연결해 실제 API·PC·휴대폰 흐름을 확인했습니다. 도면의 벽·방 위치를 주소나 면적만으로 추측하지 않습니다. GitHub에는 코드와 예시 자료만 포함하며, 실제 API 키·운영 DB·고객 업로드 자료는 포함하지 않습니다.

## AI 도면 인식·주소별 등록 도면

- `/spaces/recognize`: 이미지·PDF → AI 벽·문·창·방 추출 → 고객 실제 치수 확인 → 내 공간·3D 편집 → 원할 때 시공 요청. API 키가 없으면 가짜 인식 결과를 내놓지 않습니다.
- `/spaces/address`: 단지·주소 검색 → 단지 확인 → 동·호(선택)·평형·타입·확장 여부 → 원본 도면 확인. 갈매스타힐스 공개 기본형 7타입을 찾을 수 있고, 112A는 원본 대조 참고 배치로 시작합니다. 다른 타입의 구조를 112A로 대신하지 않습니다. 맞는 도면이 없거나 확장형이면 직접 업로드합니다.
- `/spaces/templates`: 사용 권한을 확인해 등록한 도면을 주소·단지명·타입으로 찾고 선택합니다. 운영자가 등록한 실측 도면 데이터는 아직 없습니다.
- `/admin/floorplans`: 주거 프로젝트의 구조만 복사해 등록·숨김 처리합니다. 원본 고객의 사진과 가구는 제외합니다.
- 설정 예시는 `config/environment.example`. 로컬 `.env.local` 또는 Docker `.env`에 복사해 사용하고 실제 키는 Git에 올리지 않습니다.
- 단지 검색·원본 대조 참고 배치 검사: `npm run check:apartment`, `npm run test:e2e -- apartment`. 네이버 공식 검색 API 키가 없으면 등록 자료만 검색합니다. 별도 `NAVER_SEARCH_CLIENT_ID`, `NAVER_SEARCH_CLIENT_SECRET`이 필요합니다.
- 일반 검사: `npm run check:floorplan`, `E2E_DIST=.next-ai E2E_BUILD=1 npm run test:e2e -- floorplan`. 실제 키가 로컬에 있어도 일반 E2E는 키를 끄고 고정 인식 기록으로 검사합니다.
- 정확도 수정(2026-10-05): AI가 읽은 벽·문·창 좌표를 원본 이미지의 벽선과 개구부로 다시 측정합니다. 기존 창·현관 위치 오류와 ㄱ자 방 합쳐짐을 자동으로 바로잡았고, 가상 도면 6종×2회 실제 API 호출이 모두 위치·개수·방 구분 검사를 통과했습니다. 실제 갈매스타힐스 112A의 AI 자동 인식은 실패했습니다. 성공으로 세지 않으며 원본 대조 참고 배치를 별도 제공합니다. 고객 실측 확인이 필요합니다. 재현 검사(`npm run check:floorplan-refine`)와 유료 실제 호출 결과는 [상세 문서](docs/ai-floorplans.md)를 보세요.

## 실행

Node.js 22.13 이상이 필요합니다 (내장 SQLite 사용).

```bash
npm install
npm run dev        # http://localhost:3000
```

처음 실행하면 `data/app.db`가 만들어지고 시연용 계정과 예시 프로젝트가 들어갑니다. 비밀번호는 모두 `demo1234`입니다.

| 역할 | 계정 |
| --- | --- |
| 고객 | customer@demo.kr |
| 업체 | vendor1@demo.kr, vendor2@demo.kr, vendor3@demo.kr |
| 운영자 | admin@demo.kr |

- 데이터 초기화는 `npm run data:reset -- --yes`로만 합니다(먼저 백업하고 백업 폴더는 남김). `data/` 폴더를 직접 지우면 백업까지 사라집니다.
- 시연 데이터 없이 시작하려면 `SEED_DEMO=0 npm run dev`로 실행합니다. 빈 DB의 첫 운영자는 서버 환경 변수 `ADMIN_EMAIL`·`ADMIN_PASSWORD`(10자 이상)·`ADMIN_NAME`으로 생성합니다.

## 로컬 운영용 실행(대면 테스트)

배포 전 대면 테스트는 이 컴퓨터에서 운영용으로 띄웁니다. **시작·중지·재시작은 데이터를 건드리지 않고**, 초기화와 복구는 아래 별도 명령으로만 합니다.

```bash
npm run build                 # 코드를 고친 뒤에만 다시
npm run serve:start           # http://localhost:3100 (데이터: data/)
npm run serve:restart         # 데이터 그대로 다시 띄움
npm run serve:stop / serve:status

npm run data:backup -- 이름   # 서버를 켠 채로 백업 → data/backups/<시각>-이름/
npm run data:backups          # 백업 목록
npm run data:verify -- <백업> # 무결성·건수·업로드 파일 점검
npm run data:restore -- <백업> --yes   # 서버를 멈춘 뒤. 지금 데이터를 먼저 백업하고 되돌림
npm run data:reset -- --yes            # 서버를 멈춘 뒤. 지금 데이터를 먼저 백업하고 비움(백업 폴더는 남김)
```

- 운영용 실행에서는 빈 데이터에 시연 데이터를 넣지 않습니다(`SEED_DEMO=1`일 때만). http 주소로 띄우면 로그인 쿠키의 Secure를 끕니다(`COOKIE_SECURE`).
- 메일 발송 계정이 없으면 메일은 기록만 남고, 운영자 화면 ‘메일 발송 기록’에 링크(업체 비밀번호 설정 등)가 보입니다. 대면 테스트에서는 운영자가 그 링크를 업체에게 직접 열어 줍니다.
- 운영자 배정 화면은 실제 업체와 예시 업체(시연용 계정, 실제로 응답하지 않음)를 나눠 보여 줍니다.
- `DATA_DIR`·`PORT`로 다른 데이터 폴더·포트에서 띄울 수 있습니다(복구 연습용).

## 배포

운영 배포는 [DEPLOY.md](DEPLOY.md)를 따릅니다(Docker + Caddy, 서버 한 대). 운영 환경에서는 시연 데이터를 넣지 않고, `ADMIN_EMAIL`·`ADMIN_PASSWORD`로 첫 운영자 계정을 만듭니다. 환경 변수 예시는 [config/environment.example](config/environment.example)에 있습니다. 실제 키는 서버에 따로 설정합니다.

## 흐름

내 공간 만들기(실제 치수·출입문·창·기둥) → 가구 배치 수정 → 저장(버전) → 원할 때 시공 제안 요청(고른 버전이 기준으로 고정) → (운영자) 시공사 배정 → (시공사) 같은 기준으로 비공개 견적·설계 제안 → (고객) 같은 요청 기준끼리 비교 → 상담·현장 방문 요청 → (운영자) 계약 결과 기록

공사 요청은 선택이다. 사례 탐색·저장, 공간 만들기와 배치 편집은 요청 없이 쓸 수 있다. 사진만 있거나 자료가 없으면 3D를 만들지 않고 상담 요청(`/projects/new`)으로 받는다.

## 배치 생성

`lib/layout/generate.ts`는 같은 조건에 골격 세 가지를 각각 적용한다. 골격마다 방 위치·좌석 구성·통로가 다르다.

| 목적 | 방 위치 | 좌석 | 만들지 않는 경우 |
| --- | --- | --- | --- |
| 방문객 응대 중심 | 회의실·대표실을 출입구 옆 전면에, 그 옆이 대기 공간 | 통로 건너 안쪽에 대면형 긴 책상 | 회의실·대표실이 없거나 전면 폭이 모자랄 때 |
| 직원 협업 중심 | 모든 방을 안쪽 벽에 | 스크린 없는 팀 묶음 + 스탠딩 협업 테이블 | 협업 테이블을 두면 좌석이 모자랄 때 |
| 집중 업무 중심 | 회의실·탕비실을 출입구 쪽 옆 벽에 세로로 | 칸막이를 세운 한 방향 개인석 | 세로로 놓을 깊이가 모자랄 때 |

- 요청한 좌석과 방이 모두 들어가는 골격만 배치안이 된다. 안 되는 골격은 `skipped`에 이유와 함께 남는다. 세 골격이 모두 안 되면 좌석 위주의 단일안(`compact`)을 시도하고, 그것도 안 되면 `needs_review`다.
- 배치안마다 반영 이유(`reasons`), 장단점(`pros`·`cons`), 비교 수치(`metrics`: 방문객 동선 거리, 마주 보는 좌석, 창가 좌석 등)를 좌표에서 계산해 함께 돌려준다.
- `lib/layout/coverage.ts`는 입력 항목이 배치에 반영됐는지, 가정인지, 시공사에 전달만 되는지를 정리한다.
- `npm run check:layouts`는 조건 8,080가지로 배치를 만들어 가구 겹침, 공간 밖으로 나간 물체, 닿을 수 없는 좌석·방, 가구 묶음(편집 단위) 누락, 묶음 → 다시 그리기 왕복 일치, 편집 화면과 같은 배치 검사(문 앞 750mm 임시 기준 포함)를 확인한다. 배치 규칙을 고치면 반드시 돌린다.
- 엔진은 자기가 만든 배치를 같은 검사(`lib/space/check.ts`)로 확인하고, 걸리면 다음 여유 수준을 시도하거나 그 골격을 만들지 않는다. 경고가 있는 자동 배치를 내놓지 않는다.
- `npm run check:space`는 실제 구조 입력 검사, 출입문 위치와 자동 배치 지원 범위, 서로 다른 치수의 벽·출입문·창·기둥, 회전, 서버의 편집 결과 재구성(설비 제안/확인 상태·잘못된 값 거부), 검사 규칙 정답 사례(급배수 거리·다각형 공간 밖 포함), 도면 따라 그리기의 모양 정리·축척·회전·벽 길이 맞추기를 확인한다(130개).

## 실사용 테스트용 기능 (6차)

- **자료 없이도 요청**: 요청 첫 단계에서 가진 자료를 고릅니다(도면 / 치수만 / 사진만 / 아직 없음). 실내 가로·세로를 알 때만 배치안을 만들고, 사진만 있거나 자료가 없으면 평수로 치수를 가정해 3D를 그리지 않습니다(`LayoutInput.intake`). 운영자는 ‘자료 확인’에서 고객에게 필요한 자료를 요청하고(`info_requests`), 고객은 자료를 올리고 답합니다.
- **보낸 요청 내용 보관**: 견적 요청을 보낼 때와 ‘바뀐 내용 업체에 보내기’를 누를 때마다 조건·참고 사례·파일 목록을 통째로 남깁니다(`request_revisions`, `lib/request-snapshot.ts`). 시공사 화면은 이 기록을 보여 주고 이전 내용(r1, r2…)도 열어 볼 수 있습니다. 보낸 요청에 들어간 파일은 고객이 지워도 실제로 지우지 않습니다(`files.deleted_at`). 제안은 기준 요청 내용(`quotes.request_rev_id`)이 같은 것끼리만 비교하고, 업체는 바뀐 내용을 확인한 뒤 제안을 고치거나 그대로 유지합니다.
- **놓치지 않게**: 알림은 서비스 안 알림함과 이메일(Resend, `lib/mailer.ts`, 발송 기록은 `/admin/emails`)로 갑니다. 업체 응답 기한(참여 48시간, 제안 7일)이 지나면 운영자 화면 ‘기한 안에 답하지 않은 업체’에 뜨고, 운영자는 다시 알리거나 배정을 취소하고 다른 업체를 배정합니다(`assignments.withdrawn_at`). 배정이 취소된 업체는 그 요청의 자료를 볼 수 없습니다.
- **운영 준비**: 시연 계정의 요청과 운영자가 테스트로 표시한 요청은 운영자 화면에서 실제 요청과 나눠 봅니다. 운영자가 업체를 직접 등록하고(비밀번호 설정 메일) 소개·사례를 대신 올릴 수 있습니다. 가입 시 개인정보 수집·이용 동의, 비밀번호 재설정(`/forgot`), 개인정보 처리방침 초안(`/privacy`), 상태 확인(`/health`), 백업(`scripts/backup.mjs`).

## 공간 탐색 화면과 3D 예시 (7차)

- 메인과 공간 탐색은 사진이 주인공인 큰 공간 카드(`components/explore/SpaceCard.tsx`)와 공간 종류·평수·스타일 필터(`components/explore/FilterBar.tsx`, 휴대폰은 하단 선택창)로 구성한다. 휴대폰 하단 메뉴는 홈 / 공간 탐색 / 저장 / 내 요청.

## 내 공간 만들기 · 직접 배치 · 제안 비교 (8차)

- **실제 내 공간**(`lib/space/room.ts`, `versions.room`): 직사각형 실내 가로·세로, 앞벽 출입문(모서리에서 거리·폭), 벽별 창(위치·폭, 모름/없음), 기둥(위치·크기), 천장 높이(모름이면 2,700 가정). 외벽·출입문·창·기둥은 입력한 것만 그리고, 자동 배치가 가정한 창·출입문은 버린다. 직사각형이 아닌 공간은 직사각형으로 바꾸지 않고 만들지 않는다.
- **자동 배치와 편집의 구분**: 자동 배치(`generate.ts`)는 출발점이다. 칸막이·방은 ‘자동 제안’으로 표시하고(평면 범례: 실제 벽 / 제안 칸막이 / 기둥), 가구는 묶음 단위(`Obj.g`, `LayoutOption.groups`)로 바꿔 `versions.placement`에 저장한다. 출입문이 모서리에서 2.5m 넘게 떨어지면 자동 배치 없이 빈 공간에서 시작한다. 자동 배치는 아직 기둥을 피하지 않으며 겹치면 검사에 뜬다.
- **편집**(`components/space/LayoutEditor.tsx`, `EditorPlan.tsx`): 평면에서 고르고 끌기(휴대폰은 고른 가구를 다시 눌러 끌기), 화살표 버튼(10·50·100·500mm), 숫자로 위치 입력, 90° 돌리기, 복제, 삭제, 가구 추가(`catalogItems()`), 되돌리기·다시 하기, 시작 배치 바꾸기. 3D는 같은 배치 데이터(`composeOption`)로 그린다. 저장할 때마다 새 버전(`source`: auto·edited·empty, `base_version_id`)이 생기고, 서버는 화면이 보낸 위치·방향만 받아 부품은 원본(자동 배치 묶음·카탈로그)에서 다시 채운다(`rebuildPlacement`). 탕비 설비는 10차에서 ‘자동 제안 위치 / 고객이 확인한 설비 위치’로 나눴다(아래).
- **자동 검사**(`lib/space/check.ts`): 가구끼리 겹침, 공간 밖, 기둥, 제안 칸막이, 문·출입문 앞 750mm(현재 임시 검사값), 제안 칸막이와 실제 구조, 업무석 수. 검사하지 않는 것(통로 폭·피난·법규·설비·문 열림 방향 등)을 함께 적고, 경고가 없어도 ‘시공 가능’이라고 하지 않는다.
- **보낸 배치 고정**: 요청할 때 고른 버전의 실제 구조·시작 배치·가구 위치 전체를 요청 기록(`request_revisions.snapshot.layout`)에 복사한다. 요청 뒤 고쳐 저장해도 업체는 받은 기준을 보고, ‘변경 내용 보내기’를 눌러야 새 기록(r2…)으로 같은 업체에 간다(재배정 없음, 배치 변경 내용을 문장으로 알림). 이전 기준으로 낸 제안은 그 기준(r번호)으로 남아 섞이지 않는다.
- **설계 제안**: 업체는 견적과 함께 ‘고객 배치대로’ 또는 ‘수정 제안(설명·도면·이미지 첨부)’을 낸다(`quotes.design_mode·design_note·design_files`). 첨부는 낸 업체와 그 고객만 열 수 있다(`files.category = 'proposal'`).
- **별도 후속 범위(이번 범위 아님)**: 공간 안의 벽·방문 재현(아파트·주택 방 구조), 도면 자동 인식(AI가 도면 이미지에서 벽·문을 읽어 초안을 만들고 사용자가 확인), 주소 기반 아파트 도면 검색. 칸막이·방 크기 편집, 자동 배치의 기둥 회피, 15° 단위 회전, 업체가 편집기로 그리는 수정안도 후속이다.
- 고객 테스트 준비물과 참여 조건: [docs/space-test-guide.md](docs/space-test-guide.md) (업체 제안 검증 9장, 고객 제안 비교 이해 10장, 공용 기록장 점검 11장). 업체 제안 수치는 `npm run test:report`(운영자가 ‘테스트 요청’으로 표시한 프로젝트, `-- --all`은 시연 데이터를 뺀 전체).
- 전체 기획 현황(완료·보완 필요·미개발, 결정 대기, 우선순위, 로드맵 착수 조건): [docs/platform-status.md](docs/platform-status.md)

## A~E 보완과 F 도면 따라 그리기 (10차)

- **임시 검사값·지원 범위 표시**: 문 앞 750mm는 ‘현재 임시 검사값 750mm’(`DOOR_CLEARANCE_NOTE`), 출입문 2.5m 제한은 ‘현재 자동 배치 지원 범위: 출입문이 가까운 모서리에서 2,500mm 이내’(`ENTRANCE_RANGE_TEXT`)로 마법사·편집 화면·검사·실제/가정 표에 같은 문장으로 쓴다.
- **탕비 설비**: 자동 배치가 놓은 설비는 `fixture: "proposed"`(자동 제안 위치 · 급배수 확인 전, 평면에서 점선), 고객이 ‘고객 확인: 이 자리가 실제 설비 위치예요’를 누르면 `"confirmed"`(고객이 확인한 설비 위치 — 업체 확인이 아님, 실선, 편집에서 옮기지 않음). 예전 데이터의 `locked`는 제안 위치로 읽는다(`normalizeItems`). 고객이 확인한 급배수 위치(`room.utilities`, 화면에서 ‘고객 확인’으로 표시)를 받으면, 제안 위치의 설비가 거기서 직선 3,000mm(현재 임시 알림 거리) 넘게 떨어졌을 때 거리만 알린다. 배관 연결 가능 여부는 판정하지 않는다. 상태 변경은 버전의 바뀐 점·업체에 보내는 변경 내용에 남는다.
- **휴대폰 편집**: 평면 바로 아래 가로로 넘기는 ‘가구 추가’와 편집 안내, 가구를 고르면 아래 조작판(돌리기·복제·삭제 → 화살표 → 숫자 위치 순서). 자동 검사는 걸린 개수만 보이게 접고, 저장·업체 전달 안내도 접는다.
- **테스트 문서**: 치수 차이를 ‘프로그램 치수 정확도(자동 테스트, 차이 없음)’, ‘따라 그리기 찍기 차이’, ‘사용자 측정 오차(운영자 실측 대조, 참고값 2%)’로 나눴다.
- **F 도면 따라 그리기**(`/spaces/trace`, `components/space/TraceTool.tsx`, `lib/space/trace.ts`): 도면 이미지·PDF(첫 쪽 또는 고른 쪽을 `pdfjs-dist`로 이미지로 바꿈)를 밑그림으로 띄우고 → 길이를 아는 두 점으로 축척 → 벽 모서리를 차례로 찍기(가로·세로로만, 다른 모서리와 줄 맞춤, 처음 점·닫기로 닫힘) → 출입문(벽 선 누르기, 출입문 벽이 앞벽이 되게 방향을 돌림)·창·기둥·급배수 놓기 → 벽 길이를 도면 숫자로 맞추기(다음 벽을 밂). 꼭짓점이 4개면 직사각형 `RoomModel`(자동 배치 가능), 그 밖은 `shape: "polygon"`(`outline`, 변 번호로 창·출입문 위치, 자동 배치 없이 빈 공간에서 시작). 도면을 자동으로 읽지 않으며, 기울어진 벽·곡선 벽은 아직 받지 않는다. PC 중심이고 휴대폰에서는 PC 안내를 띄운다.
- **지원 범위(11차에 화면에 명시)**: 공간 입력이 재현하는 것은 실내 외곽 형태와 출입문·창·기둥(급배수는 고객 확인 위치)이다(`SPACE_SCOPE_TEXT`). 공간 안의 벽·방문(아파트·주택의 방 구조) 재현은 후속 범위다(`SPACE_LATER_TEXT`, 실제/가정 표의 ‘후속 범위’).
- **11차 보완**: 면적은 ‘맞아요’라고 판정하지 않고 계산 면적·입력 면적·차이(㎡, %)를 보여 준다(`AreaCompare`, 10%를 넘으면 다시 확인 권유). 벽 길이를 숫자로 바꾸면 함께 바뀌는 벽(다음 벽 밀림, 그다음 벽 길이 변경)을 입력 중에 미리, 바꾼 뒤에는 주황색으로 강조하고 전후 값과 ‘이 변경 되돌리기’를 보여 준다. 따라 그리기의 다른 편집도 ‘되돌리기’로 한 단계씩 되돌린다.
- **같은 모델로 그리기**: 다각형은 칸 나누기(`cellsOf`)로 바닥, 변마다 외벽(바깥 모서리에서 두께만큼 늘림)을 만들어 3D·평면·편집 평면·인쇄·업체 화면이 같은 모양을 그린다. 공간 아닌 칸에 놓인 가구는 ‘공간 밖’으로 검사하고, 가구 추가도 그 칸을 피한다. 밑그림은 `files.category = 'underlay'`(자료 목록에서는 빼고 원본 도면은 따로 보관), 행렬(`room.underlay.m`)로 편집 평면에 겹쳐 본다. 따라 그린 공간은 ‘공간 정보 고치기’에서 같은 도면 위로 다시 연다.

## 주거 1차: 집 상담 신청 · 방 한 칸 가구 배치

사무실 테스트 기준 버전의 사본(`platform-home`)에서 개발해 검증한 뒤 합친다. 범위는 [docs/residential-scope.md](docs/residential-scope.md), 기존 데이터와의 통합·되돌리기 절차는 [docs/home-integration.md](docs/home-integration.md).

- **기존 데이터 준비**: 새 칸(공간 종류·업체 분야·방 배치)은 데이터를 열 때 자동으로 붙는다. 기존 데이터에 집 예시 5건과 예시 업체 ‘주거’ 분야를 더하려면 서버를 멈추고 `npm run data:home-setup -- --dry-run` → `-- --yes`(실행 전 백업, 여러 번 실행해도 같음). 주거 규칙 검사 `npm run check:home`.
- **공간 종류**: `projects.kind`(office/home). 집 요청은 버전 입력에 `kind: "home"`(`lib/home.ts`의 `HomeInput`)을 저장하고 자동 배치는 하지 않는다. 필수는 주거 유형·지역·공사 범위뿐이고, 입력하지 않은 값은 어디서든 ‘입력하지 않음’으로 보여 준다.
- **견적 항목**: 집은 14항목(`HOME_QUOTE_CATEGORIES`). 키가 사무실 13항목과 겹치지 않아 제안 내용으로 세트를 고른다(`categoriesOf`). 부분 공사에서 고른 공사는 ‘요청 범위’로 표시한다.
- **업체 분야**: `vendors.fields`(office,home). 운영자 배정 화면은 집 요청에서 주거 분야 업체를 먼저 보여 준다.
- **방 한 칸 배치**: `versions.rooms`(방 목록, 방마다 id·이름·배치 버전 `rev`). 방을 추가·삭제·수정하면 요청 내용의 새 버전이 생기고, 요청을 보낼 때 방별 배치가 요청 기록에 함께 남는다. 보낸 뒤 바꾼 것은 ‘변경 내용 보내기’를 눌러야 업체 기준이 된다. 방끼리 잇지 않으며 집 전체 도면으로 표시하지 않는다(‘방 한 칸 · 집 전체 아님’).
- **검사**(`lib/space/home-room.ts`): 확인할 것 4종(가구끼리 겹침, 고정 구조물과 겹침, 방 밖, 문 앞 장애물: 문 폭 × 깊이 최대 900mm)과 통로 간격 알림(편집 참고, 가구·벽·고정 구조물 사이 50mm 초과 600mm 미만, 300mm 이상 마주 볼 때, 판정하지 않음).
- **개념 가구**: 20종, 실제 상품 아님. 크기를 바꾸면 부품을 비율대로 늘리거나 줄여 평면·3D·검사·저장 후 복원이 같은 크기를 쓴다(`resizeItem`, `rebuildRoomItems`).
- **공간 탐색**: 집 방 한 칸 3D 예시 5건(`lib/seed-home-cases.ts`, 이미지는 `/render?home=h01`로 그림), 사무실·집 필터.
- **하지 않음**: 집 전체 3D·평면(다음 핵심 개발은 내부 벽·방문·방 구분), 주거 자동 배치(이번 범위 제외 · 후속 검토), 욕실·주방 설비 3D, 법규 판정, 커뮤니티·쇼핑.

## 지켜야 하는 규칙

- 자동 배치는 20~50평 직사각형 사무실만. 그 밖의 조건은 결과를 억지로 만들지 않고 "검토 필요"로 접수하거나, 내 공간에서는 빈 공간에서 시작한다. 직사각형이 아닌 공간을 직사각형으로 바꾸지 않는다.
- 공간 조건이나 배치가 바뀌면 새 버전을 만들고, 한번 저장한 버전은 고치지 않는다. 견적은 같은 요청 기록(r번호 = 같은 배치·치수·조건)끼리만 비교한다.
- 업체가 확정하지 못한 항목은 0원이 아니라 "현장 확인 필요"로 받고 합계에서 뺀다.
- 견적 항목은 금액 확정(포함·별도), 금액 미정(현장 확인 필요), 범위 제외(해당 없음)로 나눠 비교한다. 대표 금액은 "현재 산정 금액 · 부가세 포함"(포함 + 별도)이다.
- "최저"는 모든 항목의 부류가 견적끼리 같고 금액 미정 항목이 하나도 없을 때만 붙인다.
- 시공사가 참여를 확정하기 전에는 "작성 중"으로 세지 않는다("참여 검토 중").
- 제안은 임시 저장할 수 있고(자동 저장 포함) 임시 저장본은 고객에게 보이지 않는다. 제출할 때마다 제출본을 `quote_revisions`에 남기며 이전 제출본은 지우지 않는다.
- 주요 진행 상황은 알림함(`/notifications`)에 쌓인다. 메일·문자 발송은 `lib/notify.ts`의 `notify()`에 채널을 붙이면 된다(아직 없음). 시공사에게 가는 알림에는 프로젝트 이름, 상세 주소, 연락처를 넣지 않는다.
- 공통 항목 합계에는 자재·수량·공사 범위가 같다는 보장이 없다는 안내를 함께 보여 준다.
- 실적 숫자나 후기는 만들어 넣지 않는다. 예시 견적과 예시 이미지는 화면에 예시라고 적는다.
- 견적 업체는 지금 운영자가 배정한다(초기 운영 방식). 고객의 관심 업체와 참고 사례의 시공사는 배정할 때 참고로만 보여 준다. 목표는 **비공개 경쟁입찰형 시공 매칭**이다: 고객이 공사 조건을 등록하면 승인된 업체들이 참여해 가격·설계·자재·기간을 제안하고 고객이 비교해 선택한다. 업체는 다른 업체의 금액과 제안을 볼 수 없고, 최저가 자동 낙찰은 하지 않는다. 요청당 참여 업체 수는 상한이며, 다 채워지지 않아도 요청은 진행한다(고객에게 현재 참여 수를 알리고 먼저 받은 제안 확인 또는 더 기다리기). 단계와 착수 조건은 [docs/platform-status.md](docs/platform-status.md) ‘시공 경쟁 제안 로드맵’에 있다.
- 가구·조명·인테리어 소품 판매자 입점과 구매는 전체 확장 범위로 유지한다. **상품 판매(정보·사진으로 판매)와 상품 3D 배치(정확한 규격·3D 모델이 준비된 상품부터 내 공간에 놓기)는 별도 단계**이며, 공간 게시물에서 상품과 시공사를 연결한다. 로드맵 순서(커뮤니티 → 주거 3D → 상품 판매 → 상품 3D 배치)는 우선순위일 뿐 앞 단계가 끝나야 시작하는 조건이 아니며, 상품 판매는 주거 3D와 독립적으로 준비한다. 지금 MVP에는 결제·정산이 없다.
- 사례 저장(`saved_cases`, 요청서에 연결하는 참고 자료)과 관심 업체(`favorites`, 배정 참고)는 따로 관리한다. 요청서에 연결한 사례는 `project_refs`에 남고 고객·운영자·배정된 시공사가 본다.
- 색상만 다른 결과를 다른 배치안으로 보여 주지 않는다. 배치 선택과 스타일 선택은 화면에서도 따로 한다.
- 입력이 없어 정한 값은 가정으로 표시하고, 배치 계산에 쓰지 않는 정보(사진, 도면, 메모, 참고 사례)는 ‘전달만’으로 표시한다.
- 상세 주소와 연락처는 고객이 현장 방문을 요청한 업체에만 보여 준다.
- 배치안은 실측 전 개념안이며 시공 확정 도면이 아니라는 문구를 유지한다.
- 실제 요청에서는 실내 치수를 모르면 배치안·3D를 만들지 않는다(평수로 치수를 가정하는 것은 배치 체험 화면에서만).
- 사용자가 입력한 벽·출입문·창·기둥(실제)과 자동 배치가 만든 칸막이(제안), 정해 둔 값(가정)을 화면에서 나눠 보여 준다.
- 배치 검사에 걸린 곳이 없어도 ‘시공 가능’이라고 쓰지 않는다. 문 앞 750mm는 ‘현재 임시 검사값’, 급배수 3,000mm는 ‘현재 임시 알림값(거리 알림, 연결 판정 아님)’, 출입문 2,500mm는 ‘현재 자동 배치 지원 범위(엔진)’로 구분해 표시한다. 세 값의 확정은 다른 기능 개발의 일괄 선행조건이 아니다.
- 업체에 보낸 요청 내용은 고치지 않고 새 기록을 쌓는다. 시공사는 기록된 내용만 본다.


검수 보완판 테스트: `npm run check:commerce`는 독립 임시 DB에서 환불 계산·동시 처리·교환 차액·정산·상품 규격 보존을 검사하고, `npm run test:e2e -- v2-fixes`는 고객·판매자·운영자의 실제 브라우저 흐름을 검사합니다. 전체 검사는 `E2E_BUILD=1 npm run test:e2e`로 실행합니다.

수정본 시연 서버는 `DATA_DIR="$PWD/data/preview-v2-20261005" NEXT_DIST_DIR=.next-test PORT=3330 APP_URL=http://localhost:3330 COOKIE_SECURE=0 SEED_DEMO=0 npm run serve:start`로 다시 켭니다. 3100의 기존 서버와 데이터는 따로 유지합니다.

## 주소·동·층·호 조회

신청할 때는 `/projects/new`(사무실 상담), `/homes/new`(집 상담), `/spaces/new`(사무실 공간 만들기)의 첫 단계에서 바로 주소를 조회할 수 있습니다. ‘집 / 사무실’로 신청 유형을 선택하며, 집 안에서는 아파트·빌라·원룸·오피스텔을 고객이 직접 고릅니다. 현재 구현된 신청 유형은 집·사무실입니다.

주소와 동·호를 찾은 뒤 **‘신청서에 불러오기’**를 눌러야 신청 값에 반영됩니다. 검색만으로는 입력값을 바꾸거나 신청을 제출하지 않습니다. 확인된 전용면적은 집 신청에서 ㎡·전용 기준으로, 사무실 신청에서는 기존 평수 입력 단위로 변환해 채웁니다. 면적을 확인하지 못하면 예시 값으로 채우지 않습니다. 주소 검색 결과나 면적만으로 벽·방·가로·세로 치수를 만들지 않습니다. 불러온 상세 주소는 저장된 요청의 비공개 주소이며, 현장 방문 요청 업체에게만 공개됩니다.

실제 신청 흐름 검사: `tests/live/intake.cjs`에 `B`·`DB`·`P`를 지정해 실행합니다. 주소·상세주소·건축물대장 키가 연결된 격리 서버와 `.e2e-data/` DB에서만 실행합니다. 실제 데이터에 새 요청을 만들지 않도록 기본 회귀 검사에는 포함하지 않습니다.

서버 전용 `.env.local`에 `JUSO_API_KEY`(도로명주소 검색)와 `JUSO_DETAIL_API_KEY`(상세주소 검색)를 각각 설정합니다. 서로 다른 승인키입니다. 변경한 뒤 서버를 다시 시작합니다. 키를 브라우저 변수나 Git에 넣지 않습니다.

`/spaces/address`의 ‘주소·동·호로 건물 정보와 전용면적 알아보기’를 열면 주소 검색 → 내 건물 선택 → 등록된 동·층·호 선택으로 이어집니다. 상세주소 미연결·미수록·조회 실패 또는 목록에 원하는 호가 없을 때는 직접 입력할 수 있습니다. 반환한 건물·동 식별값이 요청과 다르거나 목록이 불완전하면 선택지로 쓰지 않습니다. 동·호 조회는 평면도나 호별 타입 확인을 뜻하지 않습니다.

`DATA_GO_KR_KEY`가 없을 때 실제 주소에 예시 건물 정보·면적을 표시하거나 상담 신청에 예시 면적을 채우지 않습니다. 기존 시연 주소에는 예시 표시와 함께 시연 자료를 유지합니다.

건축물대장 키는 `.env.local`의 `DATA_GO_KR_KEY`에 설정합니다. 포털의 일반 인증키와 URL 인코딩된 인증키를 모두 받으며, 요청에는 한 번만 인코딩합니다. 건축HUB의 `getBrTitleInfo`로 선택한 동의 건물 정보를 확인하고, `getBrExposPubuseAreaInfo`로 같은 지번·동·호의 전유부만 합산합니다. 공용부는 제외합니다. 표제부의 세대수·층수·연면적은 선택한 동의 수치이며 단지 전체 수치가 아닙니다.

여러 페이지를 전부 확인하고, 중복·다른 대장·불명확한 면적은 자동 입력하지 않습니다. 빈 응답·일시적 연결 실패는 최대 두 번 재시도합니다. 조회 실패·미수록 때는 확인된 건물 정보만 표시하고 전용면적은 비워 둡니다. 면적만으로 공간 모양이나 평형별 도면 타입을 추측하지 않습니다.
